MySQL 索引本质上是一种**帮助数据库快速定位数据的数据结构**。

如果没有索引：

```sql
select *
from user
where id = 100;
```

数据库只能：

```text
全表扫描

第1条
第2条
第3条
...
第N条
```

时间复杂度：

```
O(N)
```

数据量大时性能很差。

有索引后：

```text
索引结构

      |
      |
快速定位

      |
      |
数据页
```

可以快速找到目标数据。

---

## 1. MySQL索引底层使用什么数据结构？

MySQL InnoDB 默认使用：

> **B+Tree 索引结构**

注意：

不是普通的二叉树，也不是 Hash。

InnoDB：

* 聚簇索引（主键索引）
* 二级索引

底层都是 B+Tree。

---

## 2. 为什么使用B+Tree？

先看几种常见数据结构。

---

## 3. 二叉搜索树（Binary Search Tree）

结构：

```
        10

      /    \

     5      20

          /

         15
```

查询：

平均：

```
O(logN)
```

看起来很好。

但是问题：

如果数据有序插入：

例如：

```
1
2
3
4
5
6
```

可能退化：

```
1

 \
  2

   \
    3

     \
      4
```

变成链表。

查询：

```
O(N)
```

不适合数据库索引。

---

## 4. AVL树 / 红黑树

为了解决二叉树退化问题，引入：

* AVL树
* 红黑树

特点：

保持平衡。

查询：

```
O(logN)
```

为什么 MySQL 不用？

主要问题：

**树高度太高**

数据库数据量非常大。

例如：

一张表：

```
1000万数据
```

如果使用红黑树：

每个节点只能存一个 key。

高度可能：

```
20~30层
```

查询：

需要多次磁盘IO。

数据库性能瓶颈：

不是CPU，

而是：

> 磁盘IO

---

## 5. Hash索引

Hash：

结构：

```
key

 |

hash函数

 |

value地址
```

查询：

理论：

```
O(1)
```

为什么不用？

因为 Hash 不支持范围查询。

例如：

```sql
select *
from user
where age > 20;
```

Hash：

无法快速找到：

20之后的数据。

另外：

不支持：

```sql
order by
```

和：

```sql
like 'abc%'
```

---

## 6. B树（B-Tree）

B树：

一个节点可以存多个key。

例如：

```
          [20 50]

       /     |      \

   <20    20-50    >50
```

优势：

降低树高度。

但是：

数据和索引都存储在节点。

---

## 7. B+Tree（MySQL选择）

B+Tree：

结构：

```
                 Root

              [20 50]


          /      |       \


       Node     Node     Node


        |

----------------------------

叶子节点:

10 20 30 40 50 60
```

特点：

### （1）非叶子节点只存索引

例如：

```
Root:

20

50
```

不存完整数据。

这样：

一个节点可以放更多key。

---

### （2）数据全部存放在叶子节点

例如：

```
Leaf:

10 -> 数据地址

20 -> 数据地址

30 -> 数据地址
```

查询最终到叶子节点。

---

### （3）叶子节点通过链表连接

例如：

```
10 -> 20 -> 30 -> 40 -> 50
```

方便范围查询。

例如：

```sql
select *
from user
where id between 100 and 200;
```

只需要：

找到100：

然后顺序遍历。

---

## 8. B+Tree相比其他结构优势

### 对比二叉树

|      | 二叉树   | B+Tree |
| ---- | ----- | ------ |
| 节点存储 | 一个key | 多个key  |
| 高度   | 高     | 低      |
| 磁盘IO | 多     | 少      |

---

### 对比Hash

|      | Hash | B+Tree |
| ---- | ---- | ------ |
| 等值查询 | 优秀   | 优秀     |
| 范围查询 | 差    | 优秀     |
| 排序   | 差    | 支持     |
| 联合索引 | 差    | 支持     |

---

### 对比B树

|      | B树   | B+Tree |
| ---- | ---- | ------ |
| 数据存储 | 所有节点 | 叶子节点   |
| 范围查询 | 一般   | 优秀     |
| 磁盘IO | 较多   | 较少     |

---

## 9. InnoDB索引结构

这是面试重点。

InnoDB索引分为：

### （1）聚簇索引（Clustered Index）

也叫：

主键索引。

结构：

```
B+Tree

叶子节点：

完整数据行
```

例如：

表：

```sql
user
```

主键：

```sql
id
```

结构：

```
id索引

1
 |
完整用户数据

2
 |
完整用户数据
```

特点：

一张表只能有一个聚簇索引。

---

### （2）二级索引（Secondary Index）

例如：

```sql
create index idx_name
on user(name);
```

结构：

```
name索引

Jack

Tom

Lucy
```

叶子节点：

存：

```
name

主键id
```

例如：

```
Jack -> id=100
```

---

## 10. 为什么二级索引查询需要回表？

例如：

SQL：

```sql
select *
from user
where name='Jack';
```

执行：

第一步：

查询二级索引：

```
name索引

Jack

↓

id=100
```

第二步：

根据id：

查询主键索引：

```
id=100

↓

完整数据
```

这个过程：

叫：

> 回表

---

## 11. 什么情况下不用回表？

覆盖索引。

例如：

索引：

```sql
(name,id)
```

SQL：

```sql
select id,name
from user
where name='Jack';
```

因为：

索引里面已经有：

```
name
id
```

直接返回。

不需要：

回主键查询。

---

## 12. 为什么推荐使用自增主键？

面试常问。

原因：

InnoDB：

主键索引是聚簇索引。

如果：

自增：

```
1
2
3
4
```

插入：

一直追加。

磁盘页：

顺序写入。

性能好。

---

如果使用UUID：

例如：

```
a8f92...
b72ac...
```

随机插入。

导致：

* 页分裂
* 磁盘IO增加
* 索引碎片

## 13. 联合索引最左匹配原则

例如：

索引：

```sql
(name, age, address)
```

支持：

```sql
where name='Tom'
```

✅

```sql
where name='Tom'
and age=20
```

✅

```sql
where name='Tom'
and age=20
and address='BJ'
```

✅

但是：

```sql
where age=20
```

❌

原因：

B+Tree按照：

name → age → address

排序。

没有name：

无法定位。

## 15. 面试30秒总结版

MySQL InnoDB 索引底层使用的是 **B+Tree** 数据结构。

相比二叉树，B+Tree 一个节点可以存储更多索引值，树高度更低，可以减少磁盘IO；相比 Hash，B+Tree 支持范围查询、排序以及联合索引。

InnoDB 中主键索引是聚簇索引，叶子节点存储完整数据；普通索引是二级索引，叶子节点存储索引字段和主键值，查询非索引字段时需要回表。

实际项目中会根据查询场景设计联合索引，同时注意最左匹配原则和避免无效索引。
